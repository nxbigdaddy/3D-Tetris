# 3D 俄罗斯方块(Blockout 式)

真三维的俄罗斯方块:**10 × 10 底面 × 12 深的方井**,方块是**四立方体**(由 4 个小立方体拼成的三维块),
沿三个轴自由旋转,下落到底后**填满一整个水平层**才会消除。

不是「二维俄罗斯方块加个 3D 外壳」:方块有 **24 个姿态**,井只有 10×10 的一层 100 格、填满才消,贴边是常态,所以**踢墙**是必须的;
「哪一层快满了」也变成了三维里最难获取的信息。

## 立即开玩

双击 **`1-开始游戏.cmd`**(首次会自动打包),或者直接双击
[dist/3D俄罗斯方块.html](dist/3D俄罗斯方块.html) —— 自包含单文件,**零外部引用**,不需要 Node、不需要起服务器。

## 验证:一条命令,五步

```bash
node scripts/verify-all.mjs      # 等价于双击 3-一键验证.cmd
```

| 步骤 | 内容 | 耗时 |
|---|---|---|
| 1. 单元测试(规则层) | 60 项:几何、井、状态机、特效/音乐数学、模式、成绩存档 | ~0.6s |
| 2. 打包自包含单文件 | Vite 构建 + 内联 three 与 CSS | ~1.2s |
| 3. 单文件自包含自检 | **零外部引用**(这就是「双击即玩」的定义) | ~0.2s |
| 4. 浏览器端到端(`file://`) | 真实键盘走完整循环 + 截图 | ~7.7s |

端到端断言的都是**玩家能感知到的事**:画面真的在出图(帧内采样像素统计颜色种类)、画布尺寸等于视口、
**方井的投影范围落在可视区内**(不被 HUD 或按键条压住)、按键真的让方块移动和旋转、
**落地投影存在且不穿井底**、硬降真的把方块写进井里并加分且 HUD 同步、补满一层真的消层加分、
`P` 真的暂停、一直原地下落真的会把井堆满并结束。

## 表现:音效、音乐、打击感

- **音效与音乐全部程序化合成,零素材**(和上一个项目一样)—— 这是单文件能真正自包含的前提。
  移动、旋转、锁定、硬降、消层(音高随一次消几层抬高)、升级、结束、暂停各有音色。
- **背景音乐跟着局势走**:紧张度 = 等级 + 井里堆得多高,越高越快、还会多铺一层低八度脉冲。
  和声进行是 Am–F–C–G 四小节循环,音符用**前瞻式调度**排进 WebAudio 时间轴(不是到点再响,
  所以帧率抖动不会走音)。
- **打击感**:消层时每个格子炸出碎块(一次 draw call 的 `THREE.Points`)、按层数震屏、
  锁定与结束各有不同强度的抖动。震屏取「多次冲击取较大值」而不是累加 —— 累加会把画面晃到看不清。

以上全部由纯函数驱动(`src/core/effects.js`、`src/core/music.js`),所以「震屏必然收敛到 0」
「粒子必须会过期」「紧张度单调有界」这些都能在 Node 里断言,而不是盯着屏幕看。

## 难度模式与成绩

| 模式 | 方块 | 难度来源 |
|---|---|---|
| **经典** | 8 种**四立方体**(4 格) | 基础玩法 |
| **高难** | 29 种**五立方体**(5 格) | 块更大、每个块 24 个姿态更多、井里更容易堆死;下落也放慢一点让你看得过来 |

**两种模式刻意共用同一个井(10×10×12)**:难度差异全部来自方块,而不是换一个井。
好处是切模式不需要重建渲染层、层数提示也一直有效;这条约束由测试写死,哪天要换井会先失败提醒。

**成绩记录**分类保存并且**持久化到本机**(localStorage,取不到时自动退回内存版):

- 每个模式各自的最高分与最高消层;
- 总局数、累计消层;
- 上次玩的模式(下次打开就是这个模式);
- 破纪录时结束面板会显示「新纪录!」,否则说明原因并列出最高分。

存档读写**全程当作脏数据**:空/字符串/负数/NaN/别的游戏留下的同名键,都会被洗成合法值,
解析失败就当作没有存档 —— 这些都有一条一条的单元测试。写不进去(配额满、隐私模式)会明确返回
`false`,界面会标注「本次记录只在本页有效」,而不是假装存好了。

## 井的尺寸:10×10×12(以及它的后果)

底面从最初的 5×5 改成了 **10×10**,一层从 25 格变成 100 格。这不是只改一个数字的事,
两边的后果我都量了出来:

| | 5×5 | 10×10 |
|---|---|---|
| 一层格数 | 25 | **100** |
| 填满一层最少要几个四格方块 | 7 | **25** |
| 无渲染机器人实测(同种子同策略) | 213 个方块消 25 层 | **501 个方块消 16 层** |
| 渲染负载(空井 / 半满 516 格,中位帧间隔) | — | 16.70 ms / 16.70 ms(= 60fps,p95 18.4 ms) |

**结论:消层频率降到约 1/3.6,但玩法依然成立**(机器人 501 个方块消了 16 层,单层与双层都出现过)。
这是尺寸本身的后果,不是 bug。若想让节奏更接近原来,两个可调方向:
把井高从 12 降到 8~10(每层更容易堆满),或者经典模式也改用五格方块(20 个方块一层)。

帧率体检是单独的手动工具(`node scripts/check-perf.mjs`)—— **刻意不放进闸门**:
无头环境测的是墙钟时间,机器一忙就抖,「断言帧率」会变成随机失败。

## 架构:规则与渲染彻底分开

```
src/core/     纯逻辑:不 import three、不碰 DOM —— 能在 Node 里跑完整对局
  polycube.js   多立方体几何:24 个旋转、规范型、自由多立方体枚举
  board.js      三维井:占位、判定、整层消除 + 塌落
  game.js       状态机:生成/下落/旋转+踢墙/锁定延迟/消层/计分/升级/结束
  rng.js        可复现随机(方块序列与测试都靠它)
  effects.js    打击感的数学:震屏衰减、粒子生命周期(无 three、无 DOM)
  music.js      音乐数学:调式、和声、琶音、紧张度 → 速度
  modes.js      难度模式:方块集、井的尺寸、速度、计分表
  progress.js   成绩与统计:全量 sanitize + 可注入存储(所以能在 Node 里测)
src/game/     渲染层(three.js)
  render.js     方井、方块、落地投影、下一个方块预览、消层闪光、粒子、可拖拽视角
  audio.js      WebAudio 接线:程序化音效 + 前瞻式音乐调度
tests/        规则层测试
scripts/      打包、自检、端到端、无渲染对局
```

这条界线不是洁癖:三维方块的规则里能出错的地方特别多(旋转枢轴、塌落、踢墙),放在 Node 里测
比在浏览器里点快两个数量级,而且**每一条规则都能被断言钉死**。

## 已经钉死的规则

1. **四立方体恰好 8 种**,五立方体 29 种 —— 生长法 + 24 旋转规范化枚举,再和文献数字逐一对上
   (`1→1, 2→1, 3→2, 4→8, 5→29`)。这串数字能一次性把枚举或规范化里的错误逼出来。
2. **旋转绕「固定整格枢轴」,四次旋转精确复原、零漂移**。
3. **消层 = 填满整个 x-z 平面**,消完上面的方块整体塌落,**每块下落距离 = 比它低的被清层数**。
4. **锁定延迟**允许落地后微调,重置次数有上限。
5. 方块序列是**袋式随机**(每 8 个里 8 种各一次),同种子完全可复现。
6. 无渲染的贪心机器人能稳定消 25~78 层(用来验收「规则层自己是不是个像样的游戏」,
   它不进游戏、也不是验证的一部分)。

## 踩过的坑

**1. 旋转枢轴不能用包围盒的几何中心**
90° 旋转要保持整数格,枢轴必须是「整格点」或「三轴全是半格点」。而 2×3 截面的方块中心是
(半格, 整格)—— **奇偶混合**,旋转会把方块甩到格与格之间。测试里专门留了一条断言演示这个陷阱。
**解法**:生成方块时定一个固定整格枢轴,之后一直用它 —— 精确整数运算、四次精确复原、零漂移。

**2. 消层时把「被清层自己的方块」搬到下一层去了**
塌落写成了「所有层都按下面被清了几层往下挪」,被清层也被算了进去:现象是消掉一层只让高度减 1,
方块总数还不减少。**解法**:被清层直接跳过;断言「清掉一层后方块总数正好少一层格数」把它钉死。

**3. 事件队列不能由 `updateGame` 清空** —— 这个 bug 直接让**界面失灵**
「硬降」「旋转」是按键处理里**直接**调用内核的,它们的事件如果在下一次 `updateGame` 开头被清掉,
界面就永远收不到。实测现象:井口已经堆满、状态已经是 `gameover`,遮罩却还停在「已暂停」;
另一处表现是**硬降之后 HUD 的分数不动**。
**解法**:队列只由消费方排空(`drainEvents`),界面每帧排空一次,不管游戏是否在跑。
教训:**「谁产生事件」和「谁清空队列」必须解耦**,否则按键路径必然漏事件。

**4. 帧外读 WebGL 像素是读不到的**
「判断真的在出图」最直接的写法是 `gl.readPixels`,但在渲染帧之外调用拿到的是已经提交的缓冲 ——
实测只读出 **1 种颜色**,把好好的渲染判成了没渲染。
**解法**:页面暴露一个 `samplePixels()`,它在**渲染的同一帧里**采样,再用 Promise 把结果交出来。

**5. 预览视口被裁剪框裁到屏幕外**
`setViewport(px, py, size, size)` 与 `setScissor(...)` 必须一致,我把裁剪框写成了
`w - size - size`,于是「HUD 写着下一个方块 T5,画面上却看不到它」。
**教训**:同一个几何量在两处出现时,只写一份(现在是 `px`/`py` 各算一次)。

**6. 取景要靠测量,不要靠眼睛**
相机常数我先拍了两次都不对(第一版太远、井只占屏幕三分之一;第二版太近、井顶出屏)。
**解法**:页面暴露 `wellNDC()` 报出方井八个角点的投影范围,端到端断言它落在
`x ∈ [-1,1]`、`y ∈ [-0.86, 0.62]` 之内(给顶部 HUD 与底部按键条留位置),然后按数据调了两次距离。

**7. 工具链上的三个小坑**
- **PowerShell 的 `Set-Content -Encoding UTF8` 会写 BOM**,Vite 直接报
  `Unexpected token '﻿'` —— 改 JSON/JS 请用编辑工具,或事后剥 BOM。
- **`Copy-Item -Recurse` 复制 pnpm 的 `node_modules` 不完整**(符号链接结构没保住,缺 `rolldown`),
  改用 `pnpm install --offline`(本地缓存里都有,9 秒装完)。
- **.NET 的文件 API 不跟随 PowerShell 的当前目录**(`Push-Location` 对它无效),
  脚本里要用绝对路径,否则会去改另一个项目的文件。

**8. 模块初始化时调用函数,而函数用到的 `const` 还没初始化(暂时性死区)**
我在 `render.js` 里给相机加了震屏偏移 `shakeOffset`,声明写在 `applyOrbit()` 的**下面** ——
可是模块初始化时就会调用一次 `applyOrbit()`,于是直接抛
`Cannot access 'shakeOffset' before initialization`,**整个游戏白屏**。
压缩打包之后这句错会变成 `Cannot access 'c' before initialization`,几乎没有线索。
**解法**:声明放在第一次调用之前;遇到这种晦涩报错,临时把 `vite.config.js` 里的 `minify` 关掉再跑一次,
就能拿到可读的变量名。这个坑的根源是我用字符串替换插入代码,没有检查插入位置。

**9. 验证接口返回的是「格子数量」而不是「格子坐标」,断言等于空转**
移动端要断言「点按钮之后方块真的动了」,我读的字段是 `pieceCells` —— 而它其实是**格子数量**,
方块平移时根本不变,于是断言永远不可能失败(比失败更糟)。
**解法**:接口里明确分开 `cells`(坐标)与 `pieceCellCount`(数量),断言用坐标。
顺带把桌面端一条同样空转的断言一起修了。

**10. 手机上的「贴墙」是合法状态,断言必须容错**
「点前移按钮后方块位置应当变化」—— 方块已经贴着那一侧的壁时,它**本来就不该动**。
只测一个方向必然偶发失败。**解法**:反方向再试一次,断言「两个方向里至少有一个动得了」。

**11. 屏幕按键被暂停遮罩挡住**
暂停遮罩是 `inset: 0`、`z-index: 5`,而屏幕按键是 `z-index: 4` —— 暂停之后就点不到「暂停」来恢复了。
这不是 bug 而是设计(恢复本就该走遮罩上的「继续」),但**测试必须知道这件事**:
点 `#overlayButton` 而不是点屏幕按键。

**12. 手机上井底被屏幕按键挡住**
12 个按钮占了画面下方约三成,而**最底下几层正好是你要盯着放方块的地方**。
**解法**:把「底部安全区比例」告诉相机(`view.setSafeArea`),注视线随之下移(物体在画面上抬高)、
相机同时拉远;桌面端这个值是 0,取景完全不变。实测井底从 NDC −0.67 抬到 −0.45,不再被挡。
**13. 「没有存储」被当成了「存好了」**
`saveProgress(storage, progress)` 只靠 try/catch 判断成败,而 `storage?.setItem(...)` 在 `storage` 是
`null` 时**安静地什么都不做**,函数接着返回 `true` —— 调用方以为存好了,玩家以为成绩保住了。
**解法**:先判断有没有可用的存储,没有就直接返回 `false`。
教训:**一个声称「成功/失败」的接口,必须把「无处可写」也算进失败**,不能只捕异常。

**14. 又一次字符串手术翻车(这次翻了两次)**
- PowerShell here-string 里含有 JS 模板字符串 `${y}` 时,PowerShell 会先把它当自己的语法解析,**脚本直接不执行**;
- 单引号字符串里的 `` `n `` **不是换行**,于是字面量 `` `n `` 被写进了 HTML。
两次都浪费了一轮往返。**规矩定死:凡是替换文本里含 JS、模板字符串或多行结构,一律用编辑工具,不用 PowerShell 替换。**

**15. 上一轮的断言会因为这一轮的正当改动而失败**
结束面板的标题原本写死断言「必须包含『井口』」,而这一轮加了成绩记录之后,破纪录时标题会变成
「新纪录!」—— 断言失败,但**功能是对的**。
**解法**:对用户可见文案的断言要接受**一组合法值**(`井口` 或 `纪录`),而不是写死一种。
写死具体文案的断言会在文案改进时变成噪音。

**16. 换模式不一定要重建渲染层**
第一版想给高难模式一个更深的井,结果发现视图里到处是「建井时算好的常量」,切模式就得整体重建。
**解法**:两种模式共用同一个井,难度只来自方块 —— 视图一行都不用改。
这不是偷懒:它把「模式」这个概念的职责收敛到了**规则层**,渲染层只认井的尺寸。
**17. 切出窗口不暂停 = 白丢一局**
玩家去回一条消息、切个标签页,回来发现自己已经输了 —— 这是真实的体验问题。
**解法**:`blur` 与 `visibilitychange` 都触发自动暂停,遮罩会写明「窗口失去焦点,已自动暂停」。
这条也有端到端断言(派发 `blur` 事件 → 状态必须是 paused)。

**18. 「逐格碎裂」需要内核把「消掉了哪些格、什么颜色」带出来**
清层是**不可逆**的:清完再想看原来那一层有什么,已经没了。第一版只在事件里带了「第几层」,
渲染层只能整层闪一下,或者自己去猜颜色(那等于把规则抄第二遍)。
**解法**:`lockPiece` 在真正清层**之前**把被消格子的坐标与颜色记录下来,随事件交给渲染层。
教训:**当渲染层需要「历史信息」时,让规则层在事件里带上,而不是让它自己去推断。**

**19. 文案断言不能写死,文案本身也不能带 markdown**
- 引导文案里写了 `**填满一整个水平层**`,而遮罩用的是 `textContent`(不解析 markdown)——
  于是星号原样显示在玩家面前。**纯文本界面里不要写 markdown。**
- 顺带一条上文提过的:对用户可见文案的断言要接受一组合法值,写死具体字样会在文案改进时变成噪音。
**20. 井的尺寸一改,「写死尺寸」的测试与验证脚本会集体假失败**
把底面从 5×5 改成 10×10 之后,三条单元测试加两处端到端脚本**同时**失败,而规则本身完全正确:
它们铺层时写死了 `for (x < 5) for (z < 5)`,井变宽之后只铺了四分之一,于是「消层」永远不会发生。
还有一条袋式随机的断言依赖「一直硬降直到结束能抽满一袋」——井变宽之后原地堆叠只要 6 个方块就堵住井口,
根本抽不满。
**解法**:所有铺层/收集都按 `game.rules.width/depth`(端到端按 `state().dims`)循环;
抽方块改成连续 `spawnPiece`(不落位),与井的大小彻底无关。
教训:**测试里凡是出现具体尺寸,都是一个会随配置变化的隐藏假设。**

**21. 相机距离不能手推 —— 这次连着错了两次**
10×10 之后我按「高度 × 2.02」算距离:桌面端顶到 NDC 0.66(上限 0.62),
手机竖屏更糟,横向溢出到 ±1.08。原因很清楚:底面变大时靠近相机的那条边更近、投影更大,
而竖屏的水平视野本来就窄。
**解法**:换成**量一次再拟合**(`fitCamera()`)——把井的八个角点投影到 NDC,超安全区就把相机往后拉,
最多三轮;换尺寸、转屏、改安全区都会自动重fit。
这是这个项目里第三次栽在「手推可见范围」上(前两次是上一个项目的火箭被裁、西瓜藏进 HUD),**现在它是一条原则了**。

**22. 拟合的收敛容差必须小于断言的余量**
拟合是「够用就停」(误差可达 0.3%),而内部余量当时和端到端断言的阈值取得一样宽,
于是结果正好卡在阈值外 0.0008 被判失败。
**解法**:内部余量收得比断言更紧(0.88 / 0.60 / 0.84 对 0.90 / 0.62 / 0.86)。
**任何「逼近目标」的算法都要留出比验收标准更小的内部容差。**
